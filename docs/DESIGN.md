# SOP-Agent 设计文档

> **状态：作者已确认 §7 的决定（2026-11-11），评测规则（§6）冻结。**
> 项目定位：一个通用的“按标准作业流程（SOP）可靠执行”的 Agent 引擎，用电信技术支持场景做实证评测。
> 本文中“基线”指 τ²-bench 自带的 `llm_agent`；“新 Agent”指本项目实现的 Agent。

## 1. 要解决的问题

### 1.1 场景

顾客的手机没信号、上不了网或发不了彩信，打电话给运营商客服。客服 Agent 要做两类事：

- **后台操作**：查客户和线路、给流量充值、开通漫游、解除停机，这些由 Agent 自己调用工具完成。
- **远程指导**：手机在顾客手里，Agent 只能请顾客去看、去点（检查飞行模式、重插 SIM 卡、测网速等），再根据顾客的反馈决定下一步。

一道题里可能同时藏着多个故障，要按官方排障流程逐项排查，每修好一项都要请顾客重新验证。

### 1.2 评测环境

使用 τ²-bench 的电信领域（MIT 许可证，版本固定在 `c06b07d`，2026-11-10）。τ²-bench 只作为评测环境，代码不做修改。
得分看对话结束后顾客手机和后台账户的状态是否达到要求，不要求走同一条路径。

### 1.3 基线表现（开发集，模拟顾客和评分模型均为 DeepSeek）

| 指标 | 结果 |
|---|---|
| 单次成功率（74 题各 1 次） | 90.5% |
| 两次运行（73 题各 2 次） | pass^1 = 92.5%，pass^2 = 86.3%；9 道题一对一错 |
| 故障数 2 的题 / 6 个以上的题 | 15/15 / 16/20（单次运行） |
| 单题消息数中位 / 最多 | 37.5 / 106（3 次运行的数据） |

失败题的共同模式（逐题阅读对话得出）：

1. 排查几十轮后漏掉某个分支，说“所有常见原因都查过了”就转人工（7 道失败题中 5 道以转人工结束）。
2. 用错手册条件，例如只有网速为 Poor 时才查 VPN，导致漏掉真正的故障。
3. 后台操作参数错，例如充值额度不对。
4. 故障越多越容易出错。

**结论：问题不在于模型不懂，而在于长流程里没有可靠的“排查进度”。** 这是本项目要解决的核心问题。

### 1.4 流程图设置下的基线（之后比较用的就是这一组）

按 §7.1 的决定，基线改用“店规 + 分步流程图”重跑训练集 74 题各 1 次（2026-11-11）：

| 指标 | 结果 |
|---|---|
| 成功率 | 65/74 = 87.8%（文字手册版为 90.5%） |
| 失败题 | 9 道全部以转人工结束；其中 8 道是彩信题 |
| 单题消息数中位 / 单题耗时中位 | 15 次模型调用 / 67 秒 |
| 真实花费 | ¥2.30（按运行前后余额差计算） |

**8 道失败的彩信题，Agent 都没有查过流量用量，也没有充值**，而这几道题的流量都已用超。流程图的彩信路径第 3.2 步要求“用路径 2.1 检查移动数据”，流量检查在路径 2.1 的第 4 步，属于嵌套的子流程。模型没有进入子流程，彩信因此始终发不出去。

两个版本失败的题目大多不同（都失败 2 道，只在流程图版失败 7 道，只在手册版失败 5 道），说明单次运行的结果有很大偶然性，最终比较必须看多次运行。

**τ²-bench 的问题：** 2.0 版本的 `--domain telecom-workflow` 无法运行（题目声明的领域是 `telecom`，和新增的语言校验冲突）。本项目改为 `--domain telecom`，并在 `scripts/run_tau2.py` 中注册 `llm_agent_workflow`：官方 `llm_agent`，只把资料换成 τ²-bench 自己生成的流程图版本，文本与 `telecom-workflow` 设置完全相同（已逐字比对）。结果文件里的 `policy` 字段记录的是考场默认资料（文字手册），不是 Agent 实际拿到的资料。

## 2. 目标和不做的事

**目标：**

1. 提高可靠性：同一道题多次运行都成功（pass^k），而不只是单次成功率。
2. 减少不该发生的转人工：只有流程走完仍未解决时才转。
3. 每一项提升都要有对照实验和成本数据。

**不做：**

- 不修改 τ²-bench 的代码、题目和评分。
- 不针对测试集调参：测试集只在最后跑一次（见 §6）。
- 不追求官方排行榜成绩：模拟顾客和评分模型换成了 DeepSeek，分数不可直接比较。

## 3. 总体设计

核心思路：**流程由程序掌控，语言由模型负责。**

```text
顾客/工具消息
     │
     ▼
① 解析：模型把顾客的回复转成结构化结果（例：飞行模式=开）
     │
     ▼
② 更新排查账本（程序）：哪些步骤已查、结果是什么、哪些故障已修
     │
     ▼
③ 决定下一步（程序 + 模型）：按流程图找出下一个必须做的步骤
     │
     ▼
④ 生成回复（模型）：把这一步说成自然的话，或调用后台工具
     │
     ▼
⑤ 守卫检查（程序）：转人工、充值、解除停机前检查前置条件
     │
     ▼
发给顾客或调用工具
```

### 3.1 排查账本

显式保存，不靠模型记忆：

- 问题类型：无信号 / 上不了网 / 网速慢 / 彩信
- 每个流程步骤的状态：未查 / 已请求 / 已确认（附结果）
- 发现的故障和修复情况
- 修复后的验证结果
- 后台操作记录（充值额度、是否开通漫游等）

### 3.2 下一步由谁决定

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| A. 模型自由决定 | 把账本放进提示词，模型自己选 | 灵活 | 仍可能漏步，和基线差别不大 |
| **B. 程序给出“必须做的步骤”，模型可以多做** | 程序按流程图算出下一个未完成的步骤；模型负责措辞，也可以处理顾客的额外问题 | 不会漏步，又保留对话灵活性 | 流程图要编码成程序 |
| C. 完全由程序决定 | 每一步固定模板 | 最稳定 | 对话生硬，遇到流程外的问题无法应对 |

**选 B。** 这也是面试常问的“工作流和自主 Agent 怎么分工”：
- **排查顺序**有明确规则，用工作流控制。
- **理解顾客、组织语言、处理意外情况**交给模型。

### 3.3 守卫规则（程序检查，不靠提示词）

- **转人工**：账本里适用的步骤都完成，或者问题明确超出范围（如停机原因是合同到期），才允许转人工。否则退回给模型，并附上未完成的步骤。
- **充值**：额度不超过 2GB，先确认价格。
- **修复后验证**：每次修复后，必须请顾客重新测试，结果写入账本后才能进入下一步。

### 3.4 长对话的上下文

对话可能超过 100 条消息。账本已经保存了关键状态，所以提示词只保留：
1. 固定的店规和流程，放在最前面且保持不变，以便命中缓存。
2. 当前账本。
3. 最近几轮原文。

被省略的旧消息不影响决策，因为它们的结论已经写进账本。

### 3.5 和 τ²-bench 的接口

τ²-bench 每次调用 `generate_next_message`，Agent 只返回一条消息，对话循环由 τ²-bench 控制。新 Agent 用 LangGraph 实现：

- 每次需要说话或调用工具时，图在 `interrupt()` 处暂停，把这条消息交给 τ²-bench。
- 下一次 `generate_next_message` 带着顾客回复或工具结果，用 `Command(resume=...)` 继续执行。
- 账本存在图的状态里，用检查点保存。

这样对话中途中断后也能从检查点恢复。同一套代码以后也可以接入真实服务：工具调用改由自己的服务执行，Agent 核心不变。

### 3.6 通用的流程引擎

流程不写死在代码里，而是写成配置文件（YAML），由通用引擎执行。原因：电信只是第一个场景，IT 服务台、售后排障、业务办理都是“按 SOP 多步处理”，引擎应能直接复用。

**引擎负责（与领域无关）：**

- 读取流程配置，维护账本
- 根据账本算出下一个必须做的步骤
- 调用模型解析回复、生成措辞
- 执行守卫规则，记录轨迹和费用

**配置描述（每个领域一份）：**

- 问题类型和入口步骤
- 每个步骤：要检查什么、结果有哪些取值、每种结果接下来去哪一步、是否需要修复后验证
- 子流程调用，例如彩信路径先走“无信号”和“上不了网”路径
- 守卫规则的参数，例如充值上限、哪些情况允许转人工

**验证通用性：** 电信做完后，如果预算允许，再为另一个领域（如零售退换货）写一份配置，在不改引擎代码的前提下运行。这一步是加分项，不影响主线。

**边界：** 配置只描述流程。理解顾客的话、组织语言、处理流程外的问题仍由模型完成。

## 4. 技术栈

- Python 3.12、LangGraph、Pydantic（账本和结构化输出）
- DeepSeek（`deepseek/deepseek-flash`），通过 LiteLLM 调用，和 τ²-bench 一致
- pytest：用假的模型回复做离线测试，不花钱
- 自己记录每次调用的 token 和缓存命中，算出准确费用

## 5. 评测指标

| 指标 | 说明 |
|---|---|
| pass^1、pass^k | 主指标。pass^k = 同一道题 k 次都成功的比例 |
| 转人工率，以及其中“流程未走完就转”的比例 | 对应失败模式 1 |
| 单题消息数、模型调用次数 | 效率 |
| 单题费用（按缓存命中计算） | 成本 |
| 零售、航空训练题成功率 | 回归检查（可选，视预算） |

## 6. 实验规则（先定规则，再看结果）

1. **数据划分**：只用官方划分。开发和调参用训练集 74 题；测试集 40 题只在最后跑。
2. **正式评测**：测试集 40 题，基线（`llm_agent_workflow`）和新 Agent（`sop_agent_workflow`）在同一天、相同设置下各跑 3 次。评测使用提交 `844f910` 的代码，启动后不再修改 Agent。
3. **设置固定**：τ²-bench `c06b07d`；Agent、模拟顾客和评分模型都是 `deepseek/deepseek-flash`；温度 0；评分方式 `substring`。
4. **测试集只跑一次**：如果看到测试集结果后再修改 Agent，必须在报告中说明，并把修改后的成绩标为“非独立”。
5. **如实报告**：测试集结果无论好坏都写进 README，失败的题要分析原因。

| 日期 | 决定 | 原因 |
|---|---|---|
| 2026-11-11 | 主攻电信领域，零售和航空作为回归检查 | 只有电信的失败集中在同一类问题上，设计效果能被测出来 |
| 2026-11-11 | 流程写成配置，引擎通用（§3.6） | 电信只是第一个场景，避免项目被看成只适用于单一行业 |
| 2026-11-11 | 评测使用 `telecom-workflow`，重跑训练集基线 | 新旧 Agent 拿到相同资料，比较才公平（见下） |
| 2026-11-11 | 模拟顾客和评分模型使用 DeepSeek | 成本低；代价是分数不能和官方排行榜比较 |

### 7.1 给 Agent 的资料：文字手册还是分步流程图

τ²-bench 的电信领域有两种官方设置：

- `telecom`：给 Agent 的是文字手册（之前跑的基线就是这个）。
- `telecom-workflow`：给 Agent 的是分步流程图。

新 Agent 的账本按流程图组织，**所以评测应使用 `telecom-workflow`，基线也要在同一设置下重跑训练集**（74 题 × 1 次，约 ¥6）。

如果仍用 `telecom`，新 Agent 却在内部使用流程图，就等于多拿了一份资料，比较不公平。

**结论：使用 `telecom-workflow`，重跑训练集基线。** 此前用 `telecom` 测的基线保留，作为参考，不再用于比较。

### 8.1 阶段 2 结果（骨架）

- 图只有两个节点：`respond` 调用模型，`wait` 用 `interrupt()` 交出回复并等待下一条输入。两者必须分开：继续执行时 LangGraph 会从被中断节点的开头重跑，放在一起会重复调用模型（有回归测试）。
- 系统提示和基线完全相同，所以骨架和基线只差在框架上。
- 每条回复的 usage 里补上了 DeepSeek 返回的缓存命中数，`scripts/run_cost.py` 可以算出准确费用。
- 离线测试 10 个全部通过。真实试跑训练集前 3 题（都是多故障彩信题）：通过 1/3，基线同样 1/3，但过的不是同一道题；Agent 费用 $0.032，缓存命中率 97.3%。

### 8.2 阶段 3 结果（流程引擎）

- `src/sop_agent/flow.py`：通用引擎，只认“事实、路径、项目”三个概念，不含任何电信知识。
- `flows/telecom.yaml`：电信流程配置，20 个事实、4 条路径，注释标出了对应的 workflow 原文步骤编号。
- 规则：
  - 症状正常就跳过整条路径；症状异常时，逐项找到第一个未查或有故障的项目。
  - 某个事实从故障值变为正常值即算一次修复，所有症状随即清空，必须重新检查。
  - 只有某项故障无法修复，或一条路径的项目都正常而症状依旧时，才允许转人工。
- 离线测试 26 个，覆盖每条路径、修复后重查、转人工的条件，以及两个基线失败模式的回归测试：彩信题必须查流量；步骤未走完不准转人工。

**和 workflow 原文相比的简化：**

- 漫游只在顾客出行时检查。原文写的是“漫游已开但不工作时才查线路漫游”，这里只要出行就两项都查，可能多问一句。
- Step 1.3 “重置 APN 并重启”没有可检查的状态，按“必须执行一次”处理。
- 停机只区分“欠费”和“合同到期”两种原因，其他原因没有建模。
- 流程外的请求（如账单疑问）不在引擎里，交给模型按店规处理。

**尚未验证：** 引擎的输入要靠模型从顾客的自然语言回复里提取事实。提取错了，账本就会错。这一部分在阶段 4 实现，并统计提取错误率。

### 8.3 阶段 4 结果（接入引擎）

每轮流程：提取事实（单独一次调用，JSON 输出）→ 更新账本 → 引擎给出下一步 → 附上内部提示后回复 → 守卫检查。

- 下一步提示只附在本次请求的最后，不进入对话历史，否则历史每轮都变，缓存失效。
- 被守卫拦下的回复不进入历史；模型只看到拦截原因，重试最多 2 次，费用如实计入。
- 交给 τ²-bench 的回复带上本轮所有调用的用量（`llm_calls` 记录次数），`SOP_TRACE_PATH` 设置后每轮写一条轨迹。
- 注册三个版本做对照：`sop_skeleton_workflow`（只有框架）、`sop_noguard_workflow`（加流程引擎）、`sop_agent_workflow`（完整版）。
- 离线测试 14 个（合计 50 个全部通过）。

**首次真实对比（训练集，各 1 次，2026-11-11）：**

| 题组 | 基线 | 完整版 |
|---|---|---|
| 基线失败的 9 题 | 0/9 | 9/9 |
| 基线通过的 3 题（检查是否做坏） | 3/3 | 3/3 |

- 8 道彩信题都查了流量并完成充值，没有一道转人工。
- 247 轮中守卫一次也没有触发：只靠下一步提示，模型就没有过早转人工。守卫的作用这次无法判断。
- 每题 Agent 费用 $0.025，约为基线的 2.4 倍（每轮多一次提取调用，且对话走完了全程，最长 133 条消息）；缓存命中率 91.7%；实际花费 ¥1.08。
- **局限：** 题目是挑出来的，每题只跑 1 次。之前已看到单次运行偶然性很大，部分题让基线重跑也可能通过。结论要以全量训练集和测试集多次运行为准。

### 8.4 训练集完整运行和修改（2026-11-11 至 11-12）

| 版本 | 训练集 74 题（各 1 次） | 实际花费 |
|---|---|---|
| 基线（流程图资料） | 65（87.8%） | ¥2.30 |
| 完整版 v1 | 71（95.9%） | ¥6.03 |
| 完整版 v2（修改 1-3 后） | 72（97.3%） | ¥6.02 |

根据训练集失败题做了以下修改，每条都有回归测试：

1. 允许转人工时，指令要求立即调用转人工工具，不要先问顾客。
2. Agent 自己调用修复工具（开通漫游、充值、恢复线路）成功后，清空症状，要求重新检查。
3. 账户检查指令写明使用顾客所报号码对应的线路（Agent 曾查错线路）。
4. 守卫增加一条：流程要求转人工时，下一步必须是转人工工具调用（Agent 曾先解释原因，顾客随即结束对话）。
5. 已知只能转人工的故障（SIM 卡锁定、合同到期）不再先检查症状。
6. 测速事实：报出任何速度（包括 0.00 Mbps）都算已连接。
7. 停机原因：合同到期优先于欠费，因为店规规定合同到期后不能恢复线路。

修改 4-7 之后只做了小批量验证：相关的 11 题过 10 题（SIM 卡锁定 7/7），剩下的合同到期题修改 7 后连续 2 次通过。没有再完整跑一遍训练集。

**观察：**

- 守卫在 v1、v2 中几乎不触发（1335 轮中拦截 2 次，1374 轮中拦截 6 次），主要作用来自流程引擎的下一步提示。修改 4 之后守卫才有了明确用途。
- 提取并不总是一步到位：合同到期题里，提取先记成“欠费”，查到合同日期后才更正。
- 完整版每题耗时中位约 130 秒，是基线的 2 倍（每轮多一次提取调用，且流程走完全程）。

### 8.6 第二个领域：零售（2026-11-12，没有提升，未跑测试集）

**目的：** 检验引擎能否用于第二个业务。零售的流程形状和电信不同（一通电话多个请求，每个请求“找订单 → 查状态 → 收集细节 → 明确确认 → 执行”），只写一份配置不够，所以：

- 抽出引擎接口（`engines.py`）：图只调用 `observe / extract_messages / apply_extraction / next_step / summary / check_reply`。电信用适配层包住原来的 `FlowEngine`，电信的全部测试原样通过，行为不变（冻结的测试集成绩仍然有效）。
- 新增请求清单引擎（`requests.py`、`flows/retail.yaml`）。身份、订单状态、成功的写操作由代码从工具结果读取；请求列表、细节是否收齐、顾客是否明确同意由每轮的提取调用判断。
- 零售守卫：写操作前必须已核实身份、订单状态已查且允许、对应请求已明确确认；换货和改商品同一订单只能一次；不需要时不准转人工。
- `StepKind` 新增 collect / confirm / execute / deny，排障流程不会产生。MCP Server 只提供排障类流程。

**过程和花费（合计约 ¥9.2）：**

| 运行 | 结果 | 花费 |
|---|---|---|
| 第一版，基线训练集失败的 6 题 + 2 道转人工题 | 2/8 | ¥1.57 |
| 第二版，同样 8 题 | 5/8（基线失败的 6 题过了 3 道） | ¥0.46 |
| 第二版，训练集 74 题 × 1 | 62/74（基线 68/74） | ¥7.13 |

**第一版 → 第二版的修改：**

1. 删掉 `not_allowed` 请求类型。它让提取模型替 Agent 判断请求是否合法：110 题里把“未发货订单换便宜款”（合法的改商品）标成不允许，98 题第一轮就凭空多出两个不允许的请求。判断交还给回复模型，它有完整店规。
2. 按订单状态纠正请求类型（`switch_on_status`）：顾客说“换货”但订单未发货，实际是改商品，反之亦然。状态由代码读取，比模型可靠。
3. 零售的提取关闭思考（`extract_thinking: false`）。重放一次提取调用：开着思考输出 7852 token（思考约 3.3 万字符，JSON 约 700 字符），关闭后 318 token，JSON 完整。电信保持评测时的设置。
4. 轨迹按调用记录用量，之后能区分提取和回复各花多少（第二版 8 题：提取共输出 9388 token，回复 52345 token）。

**训练集退步的 8 道题（11、37、43、66、72、8、82、84）：**

| 原因 | 题目 |
|---|---|
| 模拟顾客在说“是的”的同一句话里加了 `###STOP###`，Agent 来不及执行；基线在这几题走的流程相同，只是那次顾客没提前结束 | 8、11、84 |
| 推理：选错退款原因（66）、换错一个商品（37）、四件只退了一件（82） | 37、66、82 |
| 为 104 加的“改商品前先问要不要改地址或付款方式”让 Agent 多做了一次付款方式修改，已撤回（提交 `467612c`） | 72 |
| 顾客在最后一句话里同时要求改地址和转人工，对话随即结束 | 43 |

改好的 2 道：104 靠的正是上面撤回的提示；110 这次选对了新地址（第二版冒烟测试时选错过），更像是随机波动。62/74 是撤回之前的结果，撤回后没有再完整跑。

**结论：** 零售每个请求只有三四步，基线很少漏步骤，失败主要来自推理和模拟顾客的随机性，流程引擎管不到。电信是几十步、带嵌套子流程的排障，基线最常见的错误是跳步和提前放弃，正是引擎解决的问题。训练集已看不到提升，测试集（两种 Agent × 40 题 × 3 次，约 ¥19）就不再花钱跑了。

## 9. 风险

- **提升可能不大**：基线单次已有约 90%。主要看 pass^k 和转人工率能否改善。如果没有提升，也会如实报告并分析原因。
- **把流程图编码成程序有成本**：流程分支多，编码错误会导致系统性失败。要用离线测试覆盖每条分支。
- **解析顾客回复可能出错**：顾客用自然语言描述手机状态，模型提取错了，账本就会错。需要统计解析错误率。
- **模拟顾客不完美**：DeepSeek 扮演的顾客有时不按剧本行事，部分失败不是 Agent 的错，需要逐题分析后再下结论。
